# Project Risk Register

| Risk ID | Risk Description | Possible Cause | Probability | Impact | Mitigation/Response Strategy |
|---|---|---|---|---|---|
| R1 | The approval workflow requirements (who approves what, what happens on rejection) turn out to be unclear or change once advisors/club leaders give feedback. | We're basing initial requirements on our own assumptions about how club approvals work, not on a formal interview with an actual advisor yet. | Medium | High | Confirm the approval flow with a real club officer/advisor early (even informally), document it as a simple diagram before coding it, and revisit it after each increment demo. |
| R2 | A team member is unavailable for a stretch of time due to overlapping exams/deadlines in other courses. | All three of us are taking a full course load this semester, so schedule conflicts are likely at some point. | High | Medium | Track tasks on a shared GitHub Projects board with clear owners, keep a small time buffer before each lab deadline, and make sure at least one other member understands each part of the system in case work needs to be picked up. |
| R3 | Technical difficulty implementing the budget approval logic correctly (e.g., keeping running totals consistent, avoiding double-counting). | None of us has built a system with this kind of approval + running-balance logic before. | Medium | Medium | Build a small prototype of just the budget-tracking logic early (before the full UI exists) to validate the approach, and ask the instructor/TA during office hours if we get stuck. |
| R4 | We underestimate how long the approval + budget features will take, causing later increments to be rushed. | Estimating effort is hard when it's a feature none of us has implemented before. | Medium | High | Break each increment into smaller tasks with rough time estimates, compare actual vs. estimated time after each increment, and adjust the plan for remaining increments accordingly. |
| R5 | Sensitive data (club budgets, member information) gets exposed to users who shouldn't see it. | Not enforcing role-based access properly (e.g., a regular member being able to see another club's budget). | Low | High | Enforce role checks on the back end (not just hiding buttons in the UI), and specifically test each role's access before each demo. |
| R6 | Integration issues between the front end and back end due to mismatched API expectations, since features are being split across team members. | Different members may build their part against slightly different assumptions about what data the API returns. | Medium | Medium | Agree on a simple shared API contract (endpoint names, request/response format) before starting each increment, and write it down in the repo so everyone's building against the same thing. |

Probability and Impact are rated as Low / Medium / High based on our best judgement at this stage of the project; we'll revisit and update this table as the project progresses and we learn more.
